## 状态总览

| 图中部分 | 状态 |
|---|---|
| ① RA/HCCP 注册 + 段信息合成（NPU 侧） | ✅ 完成（P2-25 验证） |
| ② TCP 控制面（capsule 携带段信息） | ✅ 正常（dump 证明数据两侧一致） |
| ②' target import 对端 jetty | ⛅ **唯一卡点**（URMA 库在 DPDK 进程里的兼容缺陷，#65 换库验证中） |
| ③ UB 数据面（jetty 拉/推） | ⏸ 未跑到（协议本身已实测——P2-19/21 裸进程双向一致） |
| ④ SPDK bdev/NVMe 落盘 | ✅ 没病（Phase 1 验证过，故障复现时也正常） |

## 要点说明

- 两侧各是**一个进程**：urma_perf / nvmf_tgt（都跑在 DPDK 运行时上）。
  图中每个节点内的两个框是同进程内的两个软件层，不是两个进程。
- 卡点在 **nvmf_tgt 进程内 URMA 传输层调用 liburma 做 import 的那一步**
  ——同一进程里 SPDK bdev/NVMe 层一切正常，说明 DPDK 进程环境本身没
  问题，病灶精确定位在 URMA 库（系统 liburma 0.0.3 与 rc2 内核的组合，
  仅在 DPDK 进程场景发病）。
- ③ 数据面协议已用裸进程双进程探针实测验证过（P2-19/P2-21 双向逐字
  节一致）——不是协议问题，纯粹被 ②' 的连接建立挡住。
