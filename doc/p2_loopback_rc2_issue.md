# SPDK 回环 rc2 兼容性问题：成因与时间线

## 一、之前为什么没有这个问题

不是"以前代码写对了所以没有"，而是**这个问题随着环境升级才诞生**：

| | Phase 1（9 月 22 日，正常） | 现在（失败） |
|---|---|---|
| 内核驱动 | rc1 / 内核 -143 | **rc2 / 内核 -159**（9 月下旬升级） |
| 系统 liburma | 升级前的版本 | **0.0.3**（升级后更换） |
| SPDK 回环 | ✅ 全零错误 | ⛔ import 失败 |

关键疏漏在中间：升级后我们做了 P2-14 复验，但复验的是 NPU 机制结论
（RA 注册、URMA 探针）——那些都走**裸进程**，绕过了 SPDK 回环路径。
直到现在做 NDS 集成，SPDK 回环才第一次在升级后的环境里跑，问题这才
现形。

## 二、是什么导致的

### 已锁死的事实链（P2-23~P2-32 十个批次排除矩阵）

1. 失败点 = 内核做 TP 资源分配（TPID 查询）时，向设备控制队列发消息失败
2. **只有 DPDK 进程**触发——裸进程做一模一样的 import 全部成功
3. 与 jetty 由谁建、创建参数、内存布局（EAL 变体）、设备选择、库版本
   均无关

### 最可能的根因（按嫌疑排序，#65 批次正在验证）

1. **新内核驱动改了 TP 分配的行为**，系统 liburma 0.0.3 没跟上——
   裸进程走的调用序列恰好绕开了新内核挑剔的那条路径，DPDK 进程的
   调用序列正撞上去。（为什么调用序列会不同？DPDK 会改变进程的内存
   布局/线程环境，liburma 据此发出的内容有差异——具体差在哪个字段，
   正是 #65 的 dump 要抓的。）
2. 或者反过来：**系统 liburma 0.0.3 在 rc2 适配时引入了回归**，
   DPDK 场景暴露。

一句话版本：**旧环境里三方（内核/库/SPDK）配合得好好的；升级换了
内核和库，新组合在 DPDK 进程这个特定场景下配合失误**。这不是谁写错
了代码，是升级后没人重验过这条路径。

## 三、正在验证的修法

#65 批次：给 nvmf_tgt 换装我们已适配 rc2 内核的 UMDK liburma
（含 TLV 适配的 7 个本地提交）——若 import 通过，修复即落地
（target 侧换库），同时这份结论对做 GDS 的同事B 也是现成的
rc2 升级适配参考。
