# NDS（NPU 直连存储）进展汇报

**2026-10-19**

## 一、项目目标一句话

NPU HBM 中的数据经 URMA（灵衢 UB）网络直连远端 NVMe SSD，全程不经过 CPU 和内存中转，复刻 GPU 版 GDS 的直连路径（基于 SPDK URMA 架构集成）。

## 二、已完成

| 事项 | 状态 |
|---|---|
| Phase 1（中转方案）单机回环全链路 | ✅ 收官，长跑 53 万次 IO 零退化 |
| Phase 2 裸驱动层双向闭环（HBM ↔ UB 盘，读/写） | ✅ 逐字节一致 |
| NPU 内存提供层（Module A：RA/HCCP 注册、段信息合成） | ✅ 完成并合入 |
| SPDK 集成层（Module B/C：段发布、target 侧 import 数据面） | ✅ 代码完成并 push |
| 代码基线切换到同事B 的 urma_enable 分支（nds_v2），增量 1710 行合入 | ✅ -M cpu 回归全通 |
| import 失败问题（存储节点 import 对端 jetty 报错） | ✅ 已解决（ABI 错位根因修复，实测 reuse 命中） |

## 三、当前卡点（一句话）

**数据面最后一跳不通**：target 发出的远端搬运请求（WR）能正常发出，但对端 HBM 数据无法被访问——表现随配置开关二选一：访问拒绝（status=4）或应答超时（status=9），DMA 确认未发生。

## 四、排查进展（30 批对照实验，全部留证）

| 已排除维度 | 结论 |
|---|---|
| ABI/结构体错位、导入令牌、导入标志、传输模式、jetty 数量 | 全部证伪 |
| 设备拓扑（同设备/跨设备）、段/TP 表形态、RA 栈完整度、DPDK 环境 | 全部证伪/出清 |
| 唯一稳定现象 | 失败形态只由"是否发布 RA jetty"决定 |
| **收敛出的唯一未测差异** | **jetty 的创建方式**：探针程序用 CCDK 方式创建的 jetty 做同样的远端读**成功**；SPDK 用自己的一套参数创建则**失败**——该差异从未做过单变量对照 |

> 佐证：同一台机器、同一硬件，独立探针（p248）以"自建 jetty + 导入对端 RA jetty + 远端读写 HBM"全流程**双向验证通过**——说明硬件链路和数据路径本身是通的。

## 五、下一步

- **#95/P2-62 判决实验（已下发，待执行）**：在探针内把 jetty 创建方式单变量替换为 SPDK 的创建序列——通过则创建方式出清、继续排查；失败则逐参数二分定位到具体差异项。
- 定位后即进入修复固化与性能基线测试。

## 六、风险与说明

- 排查在公用 133 机器上进行（与租户混跑，负载有波动）；修复结论同样适用于同事B 的 GDS 场景（其代码在该内核版本上会遇到同一堵墙）。
- 当前失败均为权限/访问语义层问题，未发现硬件或数据损坏问题。
